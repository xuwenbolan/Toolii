# Toolii — 留学生工具箱 项目书

---

## 一、项目概述

**项目名称：** Toolii（留学生工具箱）

**一句话描述：** 一个面向英国留学生的免费在线工具集合，提供证件照处理、图片压缩、文件转换等高频刚需功能。

**产品形态：** 移动端优先的 H5 网页（响应式），可在微信内直接打开使用。

**目标上线时间：** MVP 版本 2 周内上线

**核心理念：** 用免费通用工具引流，用证件照等高级功能变现。图片/文件处理由服务端完成，用户上传数据备份到后端。

---

## 二、目标用户

### 主要用户

- 英国中国留学生（核心群体）
- 需要办理申根签证、续签、各类证件的留学生
- 日常有图片/文件处理需求的学生

### 用户画像

- 年龄 18-28 岁
- 使用微信作为主要社交工具
- 价格敏感，偏好免费或低价方案
- 对 Boots 证件照 £9-12 的价格有抵触
- 经常遇到文件大小限制、格式不兼容等问题

### 用户规模估算

- QUB 中国留学生：约 3,000-4,000 人
- 全英中国留学生：约 15-17 万人
- 每年办理申根签证的留学生：保守估计数万人

### 模块一：证件照处理（核心变现功能）

| 功能 | 说明 | 技术方案 | 优先级 |
|------|------|----------|--------|
| 照片上传 | 支持拍照/相册选择 | 前端上传 + 后端存储 | P0 |
| 人脸检测 | 自动识别人脸位置 | MediaPipe Face Detection | P0 |
| 背景替换 | 白底/蓝底/红底 | rembg（多模型挡位） | P0 |
| 自动裁剪 | 按证件照标准裁剪居中 | Pillow + 自定义算法 | P0 |
| 尺寸标准库 | 申根/英国/中国/美国等 | JSON 配置文件 | P0 |
| 合规性检测 | 头部比例、表情、光线、角度 | rembg 轮廓 + MediaPipe Face Mesh + 规则引擎 | P0 |
| 排版输出 | 生成 Boots 6x4 英寸可打印图 | Pillow 排版 | P0 |
| 多张排列 | 一张 6x4 纸排多张证件照 | Pillow 布局算法 | P1 |

**背景去除模型挡位（用户可选）：**

| 挡位 | 模型 | 大小 | 速度 | 质量 | 适用场景 |
|------|------|------|------|------|---------|
| 快速 | silueta | ~43 MB | 最快 | 中等 | 要求不高、快速出图 |
| 标准 | u2net_human_seg | ~176 MB | 快 | 良好 | 日常使用 |
| 高清 | birefnet-portrait | ~973 MB | 较慢 | 极高 | 证件照精细处理 |

**照片合规性检测方案：**

检测流程：用户上传照片 -> rembg 去背景得到人物轮廓蒙版 -> MediaPipe Face Mesh 提取面部关键点 -> 逐项规则检查 -> 返回不合格项列表及提示语 -> 全部通过后进入后续处理。

| 检测项 | 方法 | 不合格提示语示例 |
|--------|------|-----------------|
| 无人脸 / 多张人脸 | MediaPipe 人脸检测数量 | "未检测到人脸" / "检测到多张人脸" |
| 脸部角度歪斜 | Face Mesh 计算 pitch/yaw/roll，超阈值报错 | "请正面面对镜头" |
| 闭眼 | 眼部关键点计算眼睛纵横比（EAR） | "请睁开双眼" |
| 张嘴 | 上下唇关键点距离比 | "请闭合嘴巴" |
| 表情过大 | 嘴角关键点上扬幅度 | "请保持中性表情" |
| 光线过暗/过亮 | 图片亮度直方图分析 | "光线不足，请移到明亮处" / "光线过强，请避开直射光" |
| 光线不均匀 | 左右脸区域亮度差值 | "面部光线不均匀，请调整光源位置" |
| 人脸太小/太大 | 人脸框面积占图片比例 | "请靠近/远离镜头" |
| 头顶/下巴被裁切 | rembg 轮廓顶点 + 面部关键点是否在图片边缘 | "头部被裁切，请调整拍摄距离" |
| 头部比例不达标 | rembg 轮廓最高点（头顶）+ Face Mesh 下巴点，计算头部占图比例 | "头部比例不符合要求，将自动裁剪调整" |
| 眼睛位置不达标 | Face Mesh 眼睛关键点相对图片位置 | "眼睛位置不符合要求，将自动裁剪调整" |
| 分辨率不足 | 图片像素低于最低要求 | "照片分辨率过低，请使用更高清的照片" |

注：头顶定位由 rembg 人物轮廓蒙版的最高点确定（MediaPipe Face Mesh 关键点仅覆盖到前额，无法覆盖头顶/头发区域），其余面部细节检测由 MediaPipe 完成。

**证件照尺寸标准（初始支持）：**

- 申根签证：35mm x 45mm
- 英国签证/护照：35mm x 45mm
- 中国护照/签证：33mm x 48mm
- 美国签证：51mm x 51mm
- 日本签证：35mm x 45mm（但要求略有不同）

**免费工具防滥用策略（不限次数，但有限流）：**

免费工具不设使用次数上限，但通过 IP/用户级限流和文件大小上限防止滥用。

| 限制维度 | 规则 | 说明 |
|----------|------|------|
| IP 级速率限制 | 匿名用户每 IP 每分钟最多 10 次请求 | 防止脚本批量调用 |
| 用户级速率限制 | 登录用户每分钟最多 20 次请求 | 登录用户适当放宽 |
| 单文件大小上限 | 图片 ≤ 20MB，PDF ≤ 50MB | 超出直接拒绝并提示 |
| 批量处理上限 | 单次最多 20 个文件，总大小 ≤ 100MB | 防止资源耗尽 |
| 并发限制 | 同一 IP/用户最多 3 个并发处理任务 | 保证服务稳定性 |

注：限流参数可根据实际服务器负载调整。被限流时返回 HTTP 429 并提示"请求过于频繁，请稍后再试"。

### 模块五：卡密与余额系统（核心变现基础设施）

**卡密定价策略：**

| 卡密类型 | 价格 | 包含次数 | 单次价格 | 说明 |
|----------|------|----------|----------|------|
| 单次卡 | ¥8 | 1 次 | ¥8/次 | 不推荐，引导用户购买多次卡 |
| 双次卡 | ¥10 | 2 次 | ¥5/次 | 主推款，性价比最高 |
| 五次卡 | ¥20 | 5 次 | ¥4/次 | 高频用户/团购场景（后续推出） |

注：不提供单次卡或将单次卡定价偏高（¥8），通过价差引导用户选择 ¥10 双次卡，提升客单价。

**卡密生成与分发：**

| 环节 | 方案 | 说明 |
|------|------|------|
| 卡密格式 | 16 位大写字母+数字 | 如 `TOOL-XXXX-XXXX-XXXX`，易读易输入 |
| 生成方式 | 后台管理工具批量生成 | 管理员指定类型和数量，批量生成并导出 |
| 分发渠道 | 自动发卡平台 | 对接第三方自动发卡平台（如发卡网），用户付款后自动发送卡密 |
| 防刷机制 | 卡密一次性使用 + 绑定兑换用户 | 兑换后标记已使用，记录兑换用户和时间 |

**自动发卡平台对接流程：**

```
用户在发卡平台下单付款
    -> 发卡平台自动发送卡密到用户邮箱/页面
    -> 用户复制卡密到 Toolii 网站兑换
    -> 系统验证卡密有效性
    -> 次数充入用户账户
```

注：自动发卡平台仅负责卡密的售卖和发送，Toolii 系统负责卡密的验证和次数充值。两者解耦，Toolii 不需要集成支付接口。

**站内兑换流程（用户视角）：**

```
用户点击"兑换卡密"（必须已登录，未登录则引导登录）
  -> 输入兑换码（TOOL-XXXX-XXXX-XXXX）
  -> 前端提交到 POST /api/credits/redeem
  -> 后端：SHA-256(输入码) -> 查库比对 hash -> 校验状态(unused)和有效期
  -> 成功：更新卡密状态为 redeemed，写入 credit_transactions，增加用户 balance
  -> 前端显示到账结果："成功充值 2 Credits，当前余额 5 Credits"
  -> 失败：提示"兑换码无效/已使用/已过期"
```

**支付接口直充流程（预留，暂不实现）：**

```
用户点击"购买 Credits"（必须已登录）
  -> 选择充值档位（如 2 Credits / ¥10、5 Credits / ¥20）
  -> 前端调用 POST /api/credits/purchase 创建支付订单
  -> 后端生成订单记录（status=pending），返回支付参数
  -> 用户完成第三方支付（微信支付/支付宝/Stripe）
  -> 支付回调通知 -> 后端验签确认 -> 更新订单状态为 paid
  -> 写入 credit_transactions（type=purchase），增加用户 balance
  -> 前端轮询或 WebSocket 通知到账结果
```

注：支付接口充值与卡密兑换共用同一套 Credits 余额体系和流水表，仅 type 字段区分来源（`recharge` vs `purchase`），无需改动消费和分享逻辑。

**付费功能扣减流程（用户视角）：**

```
用户在证件照结果页点击"无水印下载"或"6x4 排版导出"
  -> 检查登录态（未登录则引导登录）
  -> 检查余额 >= 所需 Credits（不足则提示充值，展示"兑换卡密"和"购买 Credits"入口）
  -> 扣减 Credits，写入 credit_transactions（type=consume，description 记录功能名称）
  -> 生成带签名的临时下载链接，完成下载
```

**用户余额系统：**

| 功能 | 说明 |
|------|------|
| 余额查询 | 用户可查看当前剩余使用次数 |
| 消费记录 | 记录每次使用的功能、时间、扣减次数 |
| 兑换记录 | 记录每次卡密兑换的时间、卡密类型、充入次数 |

**次数分享功能：**

用户可以将自己账户中的剩余 Credits 通过链接分享给其他用户（包括未注册用户）。

**分享流程（创建时冻结模型）：**

```
分享方点击"分享 Credits"
  -> 选择分享数量（如 1 Credit）
  -> 校验余额 >= 分享数量
  -> 立即从分享方余额扣除（冻结），写入 credit_transactions（type=share_out）
  -> 生成一次性分享链接（含唯一 token），有效期 24 小时
  -> 分享方复制链接发给朋友（微信/社交平台）

接收方点击链接
  -> 已登录：直接到账，写入 credit_transactions（type=share_in）
  -> 未登录但有账号：引导登录，登录后自动到账
  -> 未注册：引导注册，注册完成后自动到账（拉新场景）
  -> 链接状态更新为 claimed，记录接收方用户 ID

链接过期未领取
  -> 后台定时任务扫描过期的 pending 链接
  -> 自动退回 Credits 到分享方余额，写入 credit_transactions（type=share_refund）
  -> 链接状态更新为 expired
```

**分享规则：**

| 规则 | 说明 |
|------|------|
| 最小分享单位 | 1 Credit |
| 单次分享上限 | 不超过当前可用余额 |
| 链接有效期 | 24 小时，过期自动退回 |
| 领取限制 | 每个链接仅可领取一次，不可自己领自己的 |
| 同时活跃链接上限 | 每用户最多 10 个未领取的活跃分享链接（防滥用） |

**场景示例：**
- 用户 A 买了 ¥10 双次卡（2 Credits），自己用了 1 次，剩余 1 次分享给朋友 B
- B 点击链接 -> 发现没有账号 -> 注册 -> 1 Credit 自动到账 -> 免费使用一次
- B 用完觉得好用，自己也去买卡密，形成口碑传播

credit_transactions 余额流水表

├── description     描述（如 "兑换双次卡" / "证件照下载" / "分享给用户xxx"）
├── related_id      关联 ID（卡密 ID / 分享链接 ID / 支付订单 ID）
└── created_at      创建时间

share_links 分享链接表
├── id              主键
├── from_user_id    分享方用户 ID（外键）
├── to_user_id      接收方用户 ID（外键，领取后填入）
├── credits         分享次数
├── token           链接 token（唯一）
├── status          状态（pending/claimed/expired）
├── created_at      创建时间
└── expires_at      过期时间（24小时）
```

**日期一致性检查方案：**

```
用户输入出行日期：2025-07-10 ~ 2025-07-17
  -> 上传酒店确认函时：提醒"请确认酒店入住日期覆盖 7月10日-7月17日"

## 四、技术架构

### 整体架构

```
用户（微信/浏览器）
    |
    v
  前端（React + Vite + TailwindCSS）
    |
    v  API 请求
  后端（FastAPI + Python 3.13）
    |-- 图片处理层（Pillow, rembg, MediaPipe）
    |-- 文件处理层（pikepdf, python-docx）
    |-- 数据存储层（SQLite + 文件系统）
    |
    v
  Docker 部署（生产环境）
  模型文件通过 Volume 挂载
```

### 技术选型

| 层级 | 技术 | 理由 |
|------|------|------|
| 前端框架 | React + Vite | 开发效率高，打包快 |
| UI 样式 | TailwindCSS | 移动端适配方便，原子化 CSS |
| 后端框架 | FastAPI | 异步高性能，自带 API 文档 |
| 语言版本 | Python 3.13 | 最新稳定版 |
| 包管理 | uv | 极速依赖管理 |
| 数据库 | SQLite | 轻量单文件，免运维，适合项目规模 |
| 图片处理 | Pillow + rembg | Python 生态成熟，处理能力强 |
| 背景去除 | rembg（多模型） | 支持 silueta/u2net/birefnet 多挡位 |
| 人脸检测 | MediaPipe | Google 开源，精度高 |
| PDF 处理 | pikepdf / PyPDF2 | Python 原生，功能全面 |
| HEIC 转换 | pillow-heif | Python 原生处理苹果格式 |
| 扫描件处理 | OpenCV | 裁边、透视矫正、去阴影等扫描件增强 |
| 用户认证 | Google OAuth + 邮箱密码 | OAuth 零成本接入，邮箱密码零外部依赖 |
| 多语言 | i18n（初期仅中文） | 架构预留多语言支持，初期只做中文 |
| 数据分析 | Google Analytics | 免费，上线即用，需配合 Cookie 同意管理 |
| Cookie 同意 | 前端 Cookie Banner | GDPR 合规，英国/欧盟部署必须 |
| 部署 | Docker（英国/欧盟区域） | 容器化，环境一致性，服务器部署在英国或欧盟 |
| 域名 | Cloudflare 托管 | 免费 DNS + SSL |

### 关键技术决策

**前后端分离 + 服务端处理：**

- 服务端处理能力更强，不受浏览器限制
- 用户上传数据统一备份到后端，可追溯
- 背景去除模型在服务端运行更稳定，兼容性好
- 支持多模型挡位切换，用户可选择质量/速度

**模型文件挂载策略：**

- AI 模型文件不打包进 Docker 镜像，保持镜像精简
- 通过 Docker Volume 从宿主机挂载模型目录
- 支持按需下载模型，不必一次性部署所有挡位

**SQLite 选择理由：**

- 项目初期用户量有限，SQLite 完全满足需求
- 零运维成本，单文件备份方便
- 后续如需扩展，可平滑迁移到 PostgreSQL

**性能考虑：**

- 背景去除 birefnet-portrait 模型较大（~973MB），首次加载需预热
- 大图处理使用异步任务，避免阻塞请求
- 图片上传前由前端预压缩，减少传输时间

**部署区域：**

- 服务器部署在英国或欧盟区域，保证目标用户（英国留学生）的访问延迟最低
- 同时满足 GDPR 数据本地化要求

**数据保留与合规：**

- 详见「七、数据与合规」章节
- 核心原则：上传文件 24h 自动删除；卡密 hash 存储；GA 需 Cookie 同意；生物特征数据不留存

### 7.1 处理的数据类型

| 基础日志 | IP 地址、User-Agent、请求时间、请求路径 | 服务端自动采集（最小化） |
| 分析数据 | 页面浏览、功能使用事件 | Google Analytics（需用户同意） |

| 用途 | 数据 | 法理依据（UK GDPR） |
|------|------|---------------------|
| 提供工具服务（上传 -> 处理 -> 下载） | 上传文件、结果文件 | 合同履约（Article 6(1)(b)） |
| 账号与权益管理（注册、登录、Credits） | 账号信息、权益数据 | 合同履约（Article 6(1)(b)） |
| 安全风控（防滥用、异常检测、审计） | 基础日志、操作记录 | 合法利益（Article 6(1)(f)） |

### 7.3 数据保留策略

| 数据类别 | 保留时限 | 删除方式 |
|----------|----------|----------|
| 上传文件（原始 + 处理结果，普通用户） | 处理完成后 **24 小时** | 后台定时任务每小时扫描，永久删除过期文件 |
| 签证包用户材料文件 | 购买签证包后 **30 天** | 签证包用户专属延长保留期，30 天后自动删除；用户可提前手动删除 |
| 操作记录（元数据） | 账号存续期间保留 | 仅保留操作时间、功能类型、文件名等元数据；源文件删除后不可重新下载 |
| 账号信息 | 账号存续期间 | 用户可请求注销账号，注销后 30 天内清除所有关联数据 |
| 权益数据（Credits 流水） | 账号存续期间 | 随账号注销一并删除 |
| 基础日志 | **90 天** | 定期轮转清理 |
| GA 分析数据 | 遵循 Google Analytics 数据保留设置 | 建议设为 14 个月（GA 最短选项） |

### 7.4 生物特征数据处理声明

证件照处理流程涉及人脸检测（MediaPipe Face Detection / Face Mesh），需明确以下原则：

**用途严格限定：**
- 人脸检测仅用于**合规性检查**（正脸、闭眼、张嘴等）和**裁剪定位**（头部比例、眼睛位置）
- **不做**身份识别、人脸比对、人脸搜索等任何身份相关用途

**不保存派生生物特征数据：**
- 处理过程中产生的人脸关键点坐标、Face Mesh 数据、embedding 向量等中间数据**仅在内存中存在**，处理完成后立即释放
- 数据库和文件系统中**不存储**任何人脸关键点、特征向量等派生生物特征数据
- 仅保存最终处理后的证件照图片和必要的处理元数据（尺寸、背景色、合规检测结果 pass/fail）

**隐私声明须明确告知：**
- 告知用户证件照处理使用了人脸检测技术
- 说明处理目的和数据不留存的事实

### 7.5 安全措施（可执行要求）

| 层面 | 要求 | 实现方式 |
|------|------|----------|
| 传输安全 | 全站 HTTPS，禁止 HTTP 明文传输 | Cloudflare SSL + HSTS header |
| 存储权限 | 上传目录最小权限，仅应用进程可读写 | Linux 文件权限 `700`，专用运行用户 |
| 下载鉴权 | 处理结果下载链接需鉴权或短期签名，禁止可猜测 URL | 带签名的临时 URL（HMAC + 过期时间）或需登录态验证 |
| 兑换码存储 | 卡密不以明文存库 | 存储 `hash(code)`，兑换时 hash 比对验证（见 7.7） |
| 密码存储 | 用户密码不以明文存库 | bcrypt/argon2 哈希 + salt |
| 操作审计 | 兑换记录和消费记录可审计追溯 | credit_transactions 表完整记录每笔变动，含时间戳和关联 ID |
| 日志最小化 | 日志中不记录完整请求体 | 仅记录 IP、UA、路径、状态码、耗时；上传文件内容不进日志 |
| 跨域策略 | API 仅允许自家前端域名访问 | FastAPI CORS 白名单配置 |
| 速率限制 | IP/用户级限流，防止脚本批量调用和资源滥用 | FastAPI 中间件或 slowapi；详见模块四「防滥用策略」 |
| 文件大小限制 | 单文件上传上限（图片 20MB / PDF 50MB） | 前端预校验 + 后端二次校验 |

### 7.6 Cookie 同意管理

**Cookie Banner 行为规范：**

```
首次访问
  -> 页面底部/居中弹出 Cookie Banner
  -> 三个按钮：[Accept analytics] [Reject] [Manage]
  -> Manage 展开详情：
      - 必要 Cookie（始终开启，不可关闭）：会话管理、CSRF token
      - 分析 Cookie（默认关闭）：Google Analytics
  -> 用户选择后记录偏好到 localStorage

加载逻辑
  -> 仅在用户点击 Accept 或在 Manage 中开启分析后才加载 GA 脚本
  -> Reject 或未操作时不加载任何第三方分析脚本

撤回入口
  -> 页脚固定显示"Cookie 设置"链接
  -> 点击后重新弹出 Cookie Banner，允许用户随时修改偏好
```

### 7.7 兑换码规格

| 属性 | 规格 |
|------|------|
| 格式 | `TOOL-XXXX-XXXX-XXXX`（16 位大写字母 + 数字，分组易读） |
| 面额 | 可配置：+1 / +2 / +5 / +10 Credits |
| 有效期 | 可设置过期时间（默认 1 年），过期后不可兑换 |
| 使用限制 | 一次性使用，兑换后立即失效 |
| 存储方式 | 数据库中**不存储明文卡密**，存储 `SHA-256(code)`；兑换时用户输入明文 -> 计算 hash -> 与库中 hash 比对 |
| 生成流程 | 管理员工具生成明文卡密 -> 导出为 CSV/TXT（交付给发卡平台）-> 数据库仅写入 hash |
| 批次管理 | 每次生成带批次号（batch_id），便于按批次查询、按批次作废 |

### 7.8 权益模型（Credits）

Credits 为整数计量的使用权益，通过兑换码充值（当前）或支付接口直充（预留），使用付费功能时扣减。

**Credits 消耗规则：**

| 付费功能 | 消耗 Credits | 说明 |
|----------|-------------|------|
| 证件照无水印高清下载 | 1 | 单张证件照最终结果下载 |
| 证件照 6x4 排版导出 | 1 | 生成 Boots 打印用排版文件 |
| 批量处理打包导出 | 1 | 一次批量任务（不论文件数量） |
| 签证材料全流程服务 | 专项定价 ¥88 | 独立于 Credits 体系，一次性购买，包含全流程服务（证件照处理 + 文档处理 + 智能检查 + 行程单/Cover Letter 生成 + 材料打包 + 30 天云端存储） |

注：签证材料全流程服务采用独立定价（¥88/次），不通过 Credits 扣减，用户直接购买服务包。其余免费工具（图片压缩、格式转换、PDF 处理等）不消耗 Credits。

**Credits 流转类型：**

| 类型 | 方向 | 触发场景 |
|------|------|----------|
| `recharge` | +N | 用户兑换卡密 |
| `purchase` | +N | 支付接口直接购买 Credits（预留，暂不实现） |
| `consume` | -N | 使用付费功能 |
| `share_out` | -N | 创建分享链接时冻结扣除 |
| `share_in` | +N | 接收方领取分享链接 |
| `share_refund` | +N | 分享链接过期未领取，自动退回 |

**约束：**
- Credits 余额不可为负；余额不足时拒绝操作并提示充值
- 所有变动记入 `credit_transactions` 流水表，含变动后余额快照，可审计
